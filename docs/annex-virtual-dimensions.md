# Annex: Virtual vs Materialised Generated Dimensions (Informative)

This annex documents an implementation question that arises whenever a
dimension is backed by an algorithmic `provider`: should the produced
members be **materialised** (upserted as persistent Records rows) or
served **virtually** (regenerated by the algorithm on every request)?

The annex is **informative**. The only normative spec contract it
introduces is the `Feature.id` natural-key clause carried into the
`dimension-member` Building Block (see end of §4 below).

## 1. When generator-as-reader is safe

A provider can be safely served virtually — generating members on the
fly with no persistent copy — when **all** of the following hold:

- **Natural-key `id` contract.** The provided `Feature.id` is the
  natural key of the member (e.g. `dekadal:2024-D01`,
  `elevation-bands:bin_0`), not a server-minted surrogate. Regenerating
  the algorithm from the same `config` MUST produce the same `id` for
  the same member across deployments, restarts, and releases.
- **No foreign-key joins.** No downstream system stores foreign keys
  pointing into a materialised member row. (Items reference the
  dimension *value*, not the member's surrogate PK.)
- **Search implementable in the algorithm.** The provider's `search`
  capability (exact / range / like) is implementable directly against
  the generator without scanning a stored index. Temporal calendars,
  integer ranges, and in-memory trees all satisfy this.

Most well-known providers in v1.0 satisfy all three: `daily-period`
(dekadal, pentadal), `integer-range`, `static-tree`, `leveled-tree`.

## 2. When persistence is justified

Materialisation is the right call when:

- **Externally-sourced authoritative lists.** The members are not
  algorithmic — they come from a curated registry (e.g. ISO 3166
  country codes, a domain-specific code list) and the dimension API is
  a *cache* over an authoritative external source, not the source
  itself. Persistence guards against the upstream registry being
  unreachable.
- **Versioned providers with audit/point-in-time recall.** Some
  dimensions evolve over time (administrative boundaries split,
  indicator codes are renamed). When the system must answer
  "what were the members of this dimension on date X" without rerunning
  a versioned algorithm, persistence with a snapshot column is the
  pragmatic answer.

In both cases, the persisted copy is operationally a cache; the source
of truth lives outside the OGC API surface (an external registry, or a
versioned provider config).

## 3. Recommended config knob

Adopters that materialise generated dimensions SHOULD expose a
per-dimension policy:

```yaml
materialise: always | on_demand | never   # default: never
```

- `never` (default for algorithmic providers): every request runs the
  generator. No persistence. Drift is impossible because no copy
  exists.
- `on_demand`: materialise on first request and serve subsequent
  requests from the persisted copy until invalidated (e.g. by a config
  change). Useful when the algorithm is expensive enough that the
  generator should not run on every request.
- `always`: materialise eagerly at registration time. Useful for
  externally-sourced lists.

Operators MUST NOT set `materialise: always` for providers whose
output drifts from the algorithm — the `cube:dimensions` equality gate
that re-runs materialisation on config change is itself a workaround
for this drift problem.

## 4. Spec contract: Feature.id MUST equal the natural key (normative)

This annex is informative **except** for the following clause, which
is carried into the `dimension-member` Building Block as a normative
MUST:

> **REQ (dimension-member, §"Identifier"):** The `Feature.id` of a
> dimension member MUST equal the natural key of that member (the
> dimension's `code` for the member, e.g. `2024-D01`,
> `bin_0`, `ITA`). Servers MUST NOT mint surrogate UUIDs for members.
> The natural-key constraint is what makes "regenerate from the
> algorithm" safe across deployments and releases.

Without this constraint, a materialised copy and a regenerated copy of
the same dimension would carry different `id` values, and a virtual
implementation could not be substituted for a materialised one without
breaking every downstream system that records the member identifier.
